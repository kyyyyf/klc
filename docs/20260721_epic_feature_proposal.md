# Epic feature proposal (2026-07-21)

## Ключевая рамка

Эпик — это **производитель и упорядочиватель обычных тикетов**, а не второй
жизненный цикл. Каждый дочерний тикет проходит ту же машину состояний
`config/phases.yml`. Эпик добавляет ровно три вещи, которых сегодня нет:

1. обсуждение и план на уровне фичи (разговор пользователя с моделью);
2. зависимости между тикетами — пофазовые и по состоянию, с условными рёбрами;
3. групповой прогон готовых тикетов с максимально возможным параллелизмом.

Всё остальное переиспользуется как есть. Отдельная машина состояний у эпика не
заводится, отдельная инфраструктура исполнения (worktree, мультиагенты) не нужна.

## Два входа в работу

- **Единичная задача** — существующий `klc intake <KEY> "<desc>"`, без изменений.
- **Большая фича** — новый вход: пользователь проговаривает идею с моделью, на
  выходе появляется эпик (описание, набор тикетов, DAG зависимостей), и дальше
  запускается параллельное выполнение тикетов, какое позволяет граф.

Оба входа сходятся в одну машину тикетов. Эпик лишь порождает тикеты и задаёт
порядок их разблокировки.

## Модель зависимостей

Ребро зависимости описывает: **фаза `P` тикета-downstream заблокирована, пока
тикет-upstream не достигнет одной из трёх точек** (опционально — при выполнении
условия по исходу upstream).

Три точки зависимости, точно по фазе-состоянию:

| Точка | Смысл | Фаза-состояние |
|---|---|---|
| `design-accepted` | дизайн/спека выбраны | `design:ack` (M/L) или `discovery-lite:ack` (XS/S) |
| `integrated` | код работает, тесты прошли, влит | `integrate:ack` |
| `archived` | тикет полностью готов | `archived` |

**Условное ребро** несёт предикат по исходу upstream (например, `passed` — точка
достигнута без regression/rollback, либо совпадение `design_choice`). Если
условие не выполнено, зависимая фаза **не разблокируется**, а эпик помечает её как
паузу для человека — согласованное решение: провал условия останавливает
зависимый тикет на человека, а не автоотменяет и не переигрывает его.

## Модель исполнения (один пользователь)

Параллелизм рассчитан на одного пользователя, который может вести все задачи.
Планировщик эпика вычисляет **готовый набор** — тикеты, у чьей следующей фазы нет
невыполненных межтикетных предусловий. Пользователь выбирает из готового набора и
гонит тикеты существующими `klc run` / `klc next` / `klc ack`. Параллелизм — это и
есть выбор из готового набора.

Передача задачи другому человеку опирается на существующий механизм holder
(проверено по коду):

- при сдвиге фазы (`ack` / `next` / `abort`) текущий holder освобождается
  (`holder = None` — `core/phases/ack.py`, `next.py`, `abort.py`), и тикет сразу
  доступен другому;
- если тикет брошен посреди фазы, holder держится до TTL (30 минут,
  `core/skills/holder.py`), после чего другой берёт его через `klc steal`.

Никакой новой инфраструктуры исполнения не требуется. Поскольку драйв ведёт один
пользователь, эпик не упирается в отказ `autorunner` при включённом
мультипользовательском state.

## Потолок «до build» определяется зависимостями

Потолок прогона не плоский, а вычисляется из графа:

- **тикет-лист** (от него никто не зависит) останавливается на `build` для ручного
  ревью — это и есть «не дальше build»;
- тикет, от которого кто-то зависит в точке `integrated` или `archived`, эпик
  гонит настолько далеко, насколько нужно зависимым — то есть через `integrate`
  (реальный мердж) или до `archived`.

Это заодно снимает вопрос веток: раз downstream ждёт точку `integrated`, upstream
к этому моменту влит в main, и downstream работает на смёрдженном коде без стека
веток. Ревью и мердж при этом остаются за человеком — `autorunner` всегда паузит
на `integrate`.

## Гейты и зависимости ортогональны

- **Зависимость гейтит вход** в `:work` (машинный BLOCK/UNBLOCK, без участия
  человека).
- **Гейт управляет выходом** (`:ack-needed → :ack`): `conditional` проходит
  автоматически, если чисто; `decision` всегда останавливает на человека;
  `integrate` останавливает всегда.

Эти два механизма не пересекаются: фаза может быть разблокирована по зависимостям,
но всё равно упереться в свой обычный гейт, и наоборот. Выбор точки зависимости —
это ручка «раньше и рискованнее против позже и безопаснее», ортогональная
структуре человеческих гейтов.

## Артефакты и схема данных

DAG живёт централизованно в манифесте эпика, а не размазан по тикетам.

```text
.klc/epics/<EPIC-ID>/
  epic.md        # описание фичевой прозой + (опционально) приложенный артефакт
  graph.json     # узлы (тикеты) и рёбра (зависимости с точкой и условием)
```

`graph.json`:

```json
{
  "epic": "EPIC-001",
  "tickets": ["KLC-001", "KLC-002", "KLC-003"],
  "edges": [
    {"downstream": "KLC-002", "phase": "design",
     "on": "KLC-001", "point": "design-accepted"},
    {"downstream": "KLC-002", "phase": "build",
     "on": "KLC-001", "point": "integrated"},
    {"downstream": "KLC-003", "phase": "discovery-lite",
     "on": "KLC-001", "point": "integrated", "condition": "passed"}
  ]
}
```

В `meta.json` тикета добавляется только `epic: <EPIC-ID>` для группировки в
`board`. Поля `links[]` / `related_tickets[]` сегодня инертны (ничто их не пишет и
не читает) — при желании граф можно хранить и там, но отдельный манифест чище.

## Исполнение через существующую машину

- Вход в `:work` (`core/phases/next.py`, `ack.py` вызывают
  `artefacts.write_prompt_card`) получает предпроверку: если у тикета есть ребро,
  гейтящее эту фазу, проверить, что upstream достиг нужной точки и условие
  выполнено; иначе отказать с внятным сообщением. Это и есть механическое
  обеспечение зависимостей.
- Драйв одного тикета — существующий `autorunner` (`klc run`): авто-подтверждение
  `conditional`-гейтов, пауза на `decision`-гейтах, всегда пауза на `integrate`.

## Верб `klc epic`

- `klc epic new <ID>` — создать `.klc/epics/<ID>/`.
- `klc epic ready [<ID>]` — вычислить и показать готовый набор (тикет × следующая
  фаза без невыполненных предусловий).
- `klc epic status <ID>` — DAG-вид: по каждому тикету текущая фаза и «заблокирован
  чем».
- `board` — группировка по `meta.epic`.

Заведение тикетов ведёт скил-фронт через существующий `klc intake` (с `--stdin`
как способом пред-заполнить `raw.md` входным артефактом и `--kind`).

## Скил-фронт (гладкий опыт в Claude Code)

Фронт эпика — это Claude Code skill, а не последовательность CLI-заклинаний.
Пользователь ведёт один разговор, скил под капотом вызывает `intake` и планирует
прогон. По принципам интерактива (один вопрос за раз, вести с рекомендацией,
исследовать до вопросов):

1. **Постановка проблемы плюс артефакты** — разговор; приложенные файлы
   сворачиваются в `epic.md`, а в каждый тикет через `intake --stdin`.
2. **Обсуждение** — уточнение scope и границ; итог в `epic.md`.
3. **Имплементационный план уровня фичи** — декомпозиция на тикеты с обоснованием
   и DAG зависимостей (это не per-ticket `impl-plan.md`, тот появится позже внутри
   каждого тикета на его фазе design/discovery).
4. **Заведение тикетов и прогон** — скил вызывает `klc intake` на каждый тикет и
   пишет `graph.json`; затем `klc epic ready` показывает, что можно делать сейчас;
   пользователь гонит готовые тикеты, эпик разблокирует следующие по мере
   достижения точек.

## Execution trace

Тикеты 001/002/003. Треки: 001 (M), 002 (M), 003 (S). Типы гейтов из
`phases.yml`: `conditional` = A (авто, если чисто), `decision` = H (человек),
`integrate` = H всегда, `:work` = работа агента без человека (пауза только на
`[!CONFLICT]`).

### Вариант 1 — ребро на точку `integrated`

Рёбра:

```text
002.design         ← 001 @ integrated             (безусловное)
003.discovery-lite ← 001 @ integrated, ЕСЛИ 001 прошёл  (условное)
```

001 (M), ни от кого не зависит, поэтому гонится через `integrate` (от него
зависят):

```text
intake:ack       confirm-route   A
discovery:ack    approve         H①  человек смотрит spec
accept-test:ack  approve         A
design:ack       выбор опции     H②
build:ack        approve         A   (если сборка зелёная)
review:ack       approve         A если чисто / H если findings
manual:ack       passed          H③
integrate:ack    merged          H④  ВСЕГДА пауза → 001 = integrated
observe:ack      clean           A
learn:ack        archive         A   → archived
```

002 (M) — рано параллельно, потом ждёт:

```text
intake:ack       A
discovery:ack    approve         H⑤   ПАРАЛЛЕЛЬНО с 001
accept-test:ack  approve         A
design           ⛔ BLOCKED — ждёт 001 @ integrated
                 ── снимается на H④ ──►
design:ack       выбор опции     H⑥
build:ack        approve         A    → 002 стоп на build (лист)
```

003 (S) — упирается в условное ребро сразу:

```text
intake:ack       A
discovery-lite   ⛔ BLOCKED — ждёт 001 @ integrated И «001 прошёл»
                 ── после integrate 001:
                    • чисто            → UNBLOCK
                    • regression/rollback → H⑦ пауза на человека
discovery-lite:ack approve       H⑧
build:ack        approve         A    → 003 стоп на build (лист)
```

Таймлайн:

```text
Фаза A: ready = {001.discovery, 002.discovery}   003 ждёт      → H①, H⑤
Фаза B: ready = {001.design, 002.accept-test→design⛔}          → H②
Фаза C: 001 build→review→manual→integrate         002,003 ждут → H③, H④
        после H④ (integrate 001) → UNBLOCK 002.design и 003
Фаза D: ready = {002.design, 003.discovery-lite}               → H⑥, H⑧
```

### Вариант 2 — ребро на точку `design-accepted` (ранний параллелизм)

Меняем ребро 002: теперь оно снимается, как только дизайн 001 **выбран**, не
дожидаясь мерджа.

```text
002.design         ← 001 @ design-accepted        (ранний старт)
003.discovery-lite ← 001 @ integrated             (поздний старт, для контраста)
```

У 002 блок снимается на **H②** (выбор дизайна 001), а не на H④:

```text
design           ⛔ BLOCKED — ждёт 001 @ design-accepted
                 ── снимается на H② ──►
design:ack       H⑥
build:work       —   идёт, пока 001 ещё сам в build/review
build:ack        A   → 002 стоп на build
```

Таймлайн — окно параллелизма открывается раньше:

```text
Фаза A: ready = {001.discovery, 002.discovery}                 → H①, H⑤
Фаза B: ready = {001.design, 002.accept-test}                  → H②
Фаза C: ready = {001.build, 002.design→build}  ← ОБА в работе   → H⑥, затем H③,H④ у 001
        003 всё ещё ждёт integrated 001
Фаза D: после H④ (integrate 001) → UNBLOCK 003                 → H⑧
```

### Что показывают оба прогона

- **Эпик не добавляет новых человеческих гейтов.** H①…H⑥, H⑧ — это существующие
  `decision`-гейты. Единственный новый человеческий стоп — H⑦: провал условного
  ребра.
- **Точка ребра сдвигает только момент разблокировки, не структуру гейтов.**
  Вариант 2 открывает параллелизм на H②, вариант 1 — на H④.
- **Потолок «не дальше build» соблюдён для листьев** (002, 003), а 001 уезжает до
  `integrate` только потому, что от него зависят в точке `integrated`.

## Типовой шаблон двух рёбер

Пофазовая гранулярность даёт естественный безопасный шаблон:

```text
downstream.design ← upstream.design-accepted   # ранний параллельный дизайн против контракта
downstream.build  ← upstream.integrated        # сборка на реальном смёрдженном коде
```

`design-accepted` безопасно разблокирует **дизайн** downstream (проектировать
против выбранного контракта — интерфейсов из `impl-plan.md` / `design/options.md`
— можно, не дожидаясь кода). Если downstream-у на **build** нужен реальный код
upstream, для этой фазы берётся отдельное ребро на `integrated`.

**Trade-off `design-accepted`.** Ранний старт, но downstream строится против
выбранного контракта, а не против готового кода. Если реализация upstream отклонится
от выбранного дизайна, downstream может потребовать доработки. `integrated`
безопаснее (реальный код, нулевой риск расхождения), но старт позже.

## Минимальный список изменений (привязка к файлам)

- **Новое** `.klc/epics/<ID>/{epic.md, graph.json}` — манифест эпика.
- **Новое** `core/phases/epic.py` — верб `klc epic` (`new` / `ready` / `status`) +
  чтение `graph.json` и вычисление готового набора.
- **`core/phases/next.py`, `ack.py`** — предпроверка входа в `:work`: если фаза
  гейтится ребром, проверить точку upstream и условие; иначе отказать.
- **`core/phases/intake.py`** — флаг `--epic <ID>`, запись `epic` в `meta.json`.
- **`core/phases/board.py`** — группировка по `meta.epic` (сейчас группирует
  только по фазе).
- **Скил-фронт** — Claude Code skill эпика (разговор → `epic.md` + `graph.json` +
  вызовы `intake`).
- Переиспользуются без изменений: `config/phases.yml`, `core/skills/lifecycle.py`,
  `core/skills/autorunner.py` (`klc run`), `core/skills/holder.py` (передача через
  release/`steal`).

## Что НЕ делаем

- Не заводим вторую машину состояний у эпика (вариант «полноценная сущность со
  своим мини-циклом отклонён как переусложнение).
- Не строим worktree/мультиагентную инфраструктуру — параллелизм рассчитан на
  одного пользователя с готовым набором и передачей через holder.
- Не тащим зависимости downstream на несмёрдженный код через стек веток — точка
  `integrated` означает реальный мердж, и этого достаточно.

## Открытые вопросы к реализации

- Словарь условий на условном ребре: пока `passed` (точка достигнута без
  regression/rollback) и, возможно, совпадение `design_choice`. Нужен ли более
  богатый предикат — решается на фазе design тикета.
- Может ли набор тикетов и рёбер меняться по ходу эпика (динамический DAG), или
  фиксируется при создании. Базовая версия — фиксированный DAG; ветку альтернативы
  для условного провала (пере-scope downstream) можно добавить позже.
- Как `klc epic ready` учитывает holder другого пользователя в готовом наборе
  (показывать как «занято», а не как «готово»).
